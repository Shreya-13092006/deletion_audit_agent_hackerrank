# The 10 unresolved sample cases: evidence review and recommendation

## Conclusion

I reproduced the same 10 sample mismatches. I do not recommend changing prediction logic: every proposed ID is either absent from participant evidence or present without an identity link. Emitting the gold-only IDs or assigning the identity-less records by timing, order, metrics, or cohort would be a sample-keyed guess, not a generalizable audit finding.

The earlier answer had the right conservative conclusion, but its proof was too compressed and its case_23 explanation was imprecise: `case_536` is explicitly a login-reset request, so it is not a deletion case and should not be counted as a competing owner. Correcting that detail still leaves multiple plausible account assignments.

- “Improve” means add evidence-backed correct steps while preserving the 22 currently exact sample sequences and the hidden-case safety rules.
- `dataset/sample_output.csv` may be used to measure the sample mismatch, but not as evidence to generate a prediction.
- An ID appearing in an activity row is not an identity link when the row carries no subject or lookup key; a successful workflow result is also only a claim.

### What the account tie really contains

At `reported_at=2026-09-05T12:00:00Z`, the account window in `code/audit/config.py` admits the three FAILED rows for `account_7015` (`activity_3660`, 11:01:52Z), `account_410` (`activity_3662`, 11:10:55Z), and `account_9155` (`activity_3663`, 11:12:36Z). For the sample run, the NOT_STARTED sample case is `case_23`; the full evaluation also has NOT_STARTED cases 547 and 548 at that report time. Case 536 is a login reset (“Do not close the account”) and must be excluded by intent. Excluding it corrects the earlier count; it does not create a link from any remaining requester to any one of the three resource IDs. For the public sample by itself, the same NOT_STARTED report window admits all three failed resource IDs; all have the same result class and no subject link. In the separate full-evaluation input, case_536 is a non-deletion login reset and should not be attributed to deletion activity, while cases 547 and 548 also report NOT_STARTED at noon. Excluding case_536 is contract-correct, but it still does not supply the missing subject-to-account edge for the public sample or identify which failed account belongs to either full-set requester.

## Proposed code change and predicted effect

**No diff is proposed.** There is no safe general rule that emits the missing IDs or chooses among the tied resources from the available features. Removing the existing conservative tie handling would violate the no-guessing requirement. Adding sample-specific IDs or a rule like “pick the first/nearest analytics record” would also risk assigning one person’s data to another.

Predicted effect of no code change:

- All 22 currently exact sample outputs remain exact, unchanged: case_01, case_02, case_05–case_17, case_19, case_22, case_24, case_29–case_32.
- The 10 cases above remain unresolved; sample sequence accuracy stays 22/32 (0.688), with the same status and evidence scores.
- No hidden case changes, and the 192-test regression suite remains unchanged.

This is an explicit choice not to claim a score gain where the evidence does not support one.

1. Keep the predictor conservative; do not add unsupported steps to make the sample sequences match.
2. For a future dataset revision, publish a participant-visible subject-to-resource link for each retained/anonymized item, and a direct audit-record readback for case 18/20.
