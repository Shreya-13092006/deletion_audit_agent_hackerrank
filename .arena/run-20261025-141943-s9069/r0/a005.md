# Recommendation: do not force the ten remaining steps

The safe result is to keep the current predictions. The ten disagreements do not share a recoverable code defect: some gold resource IDs have no participant-facing source, while others are visible but cannot be attributed to one requester. A rule that emits them anyway would turn `sample_output.csv` into a label source or assign ownership without evidence, and could add false records to hidden cases.

## Assumptions

“Improve” means improve the agent using evidence and rules that also apply to the 518 evaluation requests. A sample-only rule copied from the answer key is not an acceptable improvement. Findings below use participant-facing files; `sample_output.csv` is used only to identify the requested mismatches.

## Proposed code change

**Unified diff: none.** The current `linker.py` links by exact email, email hash, or user ID, then follows explicit resource and recreation links. `pipeline.py` leaves unresolved workflow ties unattributed; `state.py` resolves state separately from ownership. Weakening those gates to use case-number patterns, batch order, closest timestamp, a matching metric, or one-to-one elimination would violate the no-guess rule. Adding the six analytics IDs or the missing account/audit IDs directly would be case-specific memorization.

The planner is not the source of these omissions: `planner.py` emits verification for each item it receives. Adding a blanket “verify every possible retained/anonymous record” rule would produce unverifiable records and cannot choose the correct IDs. No exact code change can be justified for these ten from the available participant evidence.

## Predicted effect and regression

No code or prediction change is proposed. Based on the supplied baseline, the predicted result on all 32 samples is unchanged: 32/32 statuses remain correct; the same 22 step sequences remain exact; the same ten remain discrepant. In particular, none of the 22 current exact matches is touched, so no regression among them is expected. This is not a claim of a measured rerun: I attempted the requested commands, but this environment’s `python.exe` is an inaccessible Windows Store shim, so neither the sample prediction nor evaluator could run here.

## Ranked recommendation

1. Keep the present evidence-backed steps; do not guess the ten IDs or owners.
2. For case_23, retain the system’s current ambiguity handling until a participant-facing lookup, identity link, or other ownership-bearing record breaks the tie. Do not use the gold’s choice to train a tie-break.
3. For the anonymous analytics and absent account/audit cases, improve only if new participant-facing evidence is supplied that links the resource ID to the user or explicitly scopes that ID. Then add a general parsing/linking rule and regression cases built from that evidence, and rerun the sample scorer and full unit suite.
