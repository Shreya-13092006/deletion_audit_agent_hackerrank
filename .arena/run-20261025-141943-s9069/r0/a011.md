## Change proposal and predicted effect

**No unified diff is proposed for the ten unresolved cases.** There is no generalizable evidence-driven code change that supplies the missing ownership keys. Based on the current results and the evidence above, leaving outputs unchanged predicts: all 32 statuses remain correct; step precision/recall/F1 and evidence accuracy remain at the reported values; exact sequences remain 22/32; and the same ten cases remain unresolved. The 22 current exact matches are untouched. Any rule that appends every null-identifier analytics record from a batch would add records to unrelated people’s answers and violate ownership and completeness checks. Any rule that assigns the next account by event time or ID order is an arbitrary join and can misattribute records on hidden cases.

The parser issue mentioned in the baseline is not an outstanding change here: `code/audit/parsers/logs.py` already converts `retained_order_loaded` into a legal-hold presence observation, and `code/tests/test_identity_and_linking.py` plus `code/tests/test_parser_coverage_and_verifier.py` already cover the trace subject and general log coverage. The existing docs report that this fixed case_220 and left the sample sequence count at 22/32. Repeating that patch would be a no-op, not an improvement to these ten cases.

## Ranked recommendation

1. Keep the current predictions for the ten cases. This is the only option consistent with the no-invention/no-case-shortcut rules and protects the 22 exact matches.
2. If the challenge data owner can add participant-visible evidence, request explicit subject/resource linkage for the three absent target IDs, an account-to-request trace for the 9/5 deletion batch, and a pre-anonymization linkage ledger for the six analytics records. Then implement and test a general linkage path; do not infer ownership from timestamps, batch adjacency, metrics, product activity, or the gold output.
3. Retain the already-implemented `retained_order_loaded` parser and coverage tests as a separate general improvement for case_220. It is evidence-backed and useful, but it does not solve any of these ten sample mismatches.

### Assumptions

“Improve” means improve the agent under the stated evidence and anti-hardcoding rules, not maximize sample exact-match score by copying the gold. Resource ownership requires a participant-visible identifier or explicit resource link. A successful activity row can support workflow history, but not requester ownership by itself.
