# The 10 unresolved sample cases: evidence review and recommendation

## Conclusion

I reproduced the ten reported sample mismatches. I recommend no prediction-logic change: for each expected step, the participant-facing evidence either does not contain the target resource or does not link it to the requester. Emitting those steps through sample IDs, suffix patterns, event ordering, or timing would be a guessed assignment, not an evidence-backed audit result. The existing engine therefore remains unchanged.

The prior investigation's account-window explanation needs one correction: `case_536` is a login-reset request, not a deletion request, and must not be counted as a competing deletion owner. Excluding it does not resolve the actual ambiguity: `activity_3660`, `activity_3662`, and `activity_3663` remain three failed account deletes without subject keys, while the relevant requests have no evidence edge to any one of them.

## Method and constraints

I used participant-facing files only to decide ownership and state. `sample_output.csv` is useful to measure which steps differ, but it is not an evidence source and was excluded from searches for resource IDs. A resource in an activity row, a successful workflow claim, or a compliant-looking record is not enough to link that resource to a person. Evidence captured after a case's `audit_at` cannot resolve it.

The requested sample run and verbose scorer reproduced 32/32 status accuracy, 0.995 step precision, 0.948 step recall, 0.971 step F1, 1.000 evidence accuracy, and 22/32 exact sequences. The focused resource-ID search covered `dataset/` excluding `sample_output.csv`, plus the shipped extracted PDF/image text in `code/cache/`. The prior run's focused search script is not required to understand the findings below; each claim identifies the participant-facing file or row to inspect.

## Proposed change and predicted effect

**No code change is proposed.** No generalizable rule in the available evidence can safely emit these ten expected steps. Adding a rule to choose the first, nearest, same-window, or similarly numbered resource would create false ownership links and could damage hidden cases. A special-case list would violate the no-case-specific-shortcuts rule.

With no change, all 22 currently exact sequences remain unchanged: cases 01, 02, 05–17, 19, 22, 24, and 29–32. The same ten cases remain unresolved; sequence accuracy stays 22/32 (0.688), with the same reported status, step, and evidence metrics. The prediction behavior on hidden cases is unchanged. The regression suite remains unaffected because no source file is edited.

## Verification and recommendation

The sample engine run and verbose scorer reproduced the supplied metrics and mismatch set. The repository's regression suite was previously run successfully (192 tests). No project source, `output.csv`, or dataset file was changed for this review.

Ranked recommendation:

1. Keep the current conservative prediction behavior; do not add unsupported resource ownership.
2. For a future participant-data revision, add direct subject-to-resource evidence for anonymized analytics rows and retained audit records, and subject-linked target references for absence checks.
3. Preserve the existing no-guessing rule for account activity windows; a shared timestamp or operation result is not a subject link.
