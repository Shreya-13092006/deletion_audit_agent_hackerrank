# Assessment: the ten sample differences are not safely repairable

## Decision

I recommend **no prediction-code change for these ten cases**. The current result is reproducible: I ran the no-LLM sample pipeline into the arena scratch directory and compared it with `sample_output.csv`; it reports exactly these ten differences, with status accuracy 1.000, evidence accuracy 1.000, and sequence accuracy 22/32. The differences fall into two categories: IDs that the participant evidence does not link to the requester, and non-identifying or future-only records whose ownership cannot be established. A rule that forces the gold steps would rely on answer leakage, a name/number convention, or a tie-break unsupported by evidence.

That conclusion is narrower than saying the underlying cases are unknowable in every conceivable system: it means the supplied participant-visible inputs do not justify the requested ownership or state claim under AGENTS.md §§6.5–6.7. No unified diff is appropriate. Keeping the pipeline unchanged has a predicted effect of **zero changes across all 32 samples**, preserving the 22 existing exact matches and all current per-step matches; it also avoids regressions on hidden cases from guessing.

### Search scope and reproducibility

I re-ran `code/main.py --no-llm --split sample` and `code/evaluation/main.py --pred <scratch>/current.csv -v`. For exact resource IDs, I searched participant evidence and the identity, audit, activity, and request CSVs (excluding `sample_output.csv` as a source of predictions). The direct hits for the analytics IDs are the unlinked evidence_92 export entries and, for analytics_9406, the evidence_94 readback lines described above. Exact searches for `account_004`, `audit_record_6645`, and `audit_record_5569` return no participant-data hits; the only apparent `account_410` substring in evidence is `account_41038`, an unrelated profile lookup with a different complete resource ID. The case_23 candidate enumeration was repeated over all 518 requests, not only the public sample subset.

The requested full unit suite was attempted using the desktop bundled Python. It ran 173 tests but ended with 26 errors because Windows sandbox permissions denied writes to the runtime's default temporary directory (`PermissionError` under `AppData\Local\Packages\sandbox...\Temp`); this is an environment limitation, not evidence of a code regression. The pipeline/evaluator sample run itself completed normally with zero output validation problems.

## Why tempting fixes fail

- **Derive IDs by suffix or sequence.** `case_04 → user_04 → account_004` appears plausible, but the evidence does not encode that mapping. A naming convention would misattribute resources in the 518-case population.
- **Treat every identifier-free analytics profile in a timed batch as the requester's.** These batches include several people. It converts shared workflow timing into ownership and violates the no-guessing rule.
- **Break case_23's tie by closest timestamp.** The implementation already applies nearest time after status/support ranking, yielding account_9155. Reversing the ordering to force account_410 is arbitrary; the same choice rule would affect other equally timed workflow matches.
- **Always add a retained audit check.** Retention policy says what to do once a subject-linked record is found. It does not identify record IDs absent from the evidence or establish their owners.

## Ranked recommendation

1. **Leave these ten predictions unchanged.** There is no evidence-backed generalized change that improves them; forcing exact-match gains would encode ungrounded associations.
2. If the dataset contract is later amended to make these cases resolvable, expose a participant-facing account-to-subject link for case_04/23, subject linkage or lookup key for each anonymized analytics row, and the retained audit-record identifiers and ownership for cases 18/20. Then implement linkage from those facts, not from the expected output.
3. Keep the independent parser-coverage issue documented separately from this sample task. It may merit its own fix and regression, but it cannot recover any of the ten missing ownership links and should not be mixed into their score-driven changes.

## Assumptions

- `sample_output.csv` is used only to identify the requested discrepancies, never to derive IDs or prediction logic.
- A future verification step still needs a grounded resource ID; an empty `evidence_id` does not authorize inventing that ID.
- Evidence is interpreted at or before each case's `audit_at`, per the project contract.
